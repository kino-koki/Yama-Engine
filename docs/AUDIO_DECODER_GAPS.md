## 第四轮：两个确定性 bug 的真修（保留历史）

### V1 · Vorbis MDCT 归一化（位级修复）

`MdctBackward` 原写 `twoOverN = 4.0 / n`。谐波级诊断显示中间 6 段 corr 0.9994+、
相位仅差 0.78°，唯独 `rms=0.00437`（幅度缩小约 230 倍）→ 不是算法精度，是全局标量。
根因：Vorbis 的 `floor × residue` 输出已是归一化频谱，逆变换不该再带 `1/n`。
改为 `norm = 1.0` 后 `corr=1.000000 / maxDiff=0.00000 / rms=1.000000`，
前 10 个样本逐位相同，8 段全 1.0 —— **逐样本匹配 libsndfile 参考**。

### M1 · MP3 Xing/LAME gapless 裁剪

本地解析 `sine16k_mono.mp3`：Xing @ 13（flags=0xf, frames=16）、LAME3.100 @ 133
（`enc_delay=576`, `enc_padding=640`）；17 个物理帧 × 576 = 9792 样本，
`16×576 − 576 − 640 = 8000`。原 `DecodeAll` 把元数据帧计入 PCM 且完全不裁剪，
输出 9792。实现 `ParseGapless()` + 裁剪后 corr 0.90764 → **0.99263**（越过 0.97），
末段 0.305 → 0.987。但 `maxAbsDiff=0.24488` 仍未达 5e-2。

### 真因：gapless 口径里 `enc_delay` 被重复扣减

`DecodeAll` 做了两件重复的事：

1. 循环里用 `!(gap.metaFrame && first)` **排除 Xing 元数据帧的 576 个 PCM**；
2. 裁剪阶段又把 `enc_delay=576` 当作 `output` 内的**起点偏移**跳一次（`skip=576`）。

但 LAME 的 `enc_delay` 正是由「元数据帧不属于音频流」这一步承载的 ——
它只该参与**有效长度**计算，不该再作为起点偏移。旧的双重扣减把窗口整体
后移 576 样本（`full[1152..9152)`），丢掉第一个有效音频帧，并把
`enc_padding` 区之前的尾部过渡样本纳入输出，那里恰有 74 个 |err|>0.05 的样本。

**修法**（`Mp3Decoder.cs`）：

```
keep = output.Count - encDelay - encPadding   // 9216 - 576 - 640 = 8000
trimmed = output[0 .. keep)                   // 起点不再偏移
```

窗口变成 `full[576..8576)`，逐样本对齐后直接达标。

### 同时修掉的测试工具缺陷：周期信号的伪峰

参考波形是 `0.5015·sin(440Hz) + 0.1998·sin(1320Hz+φ)` @16kHz，
440/16000 = 11/400、1320/16000 = 33/400 → **严格 400 样本周期**。
旧的「步长 16 粗搜 + ±16 精搜」在周期信号下必然停在任意一个伪峰
（实测 off=-1584，与真实峰 off=-1329 差 255 样本 → 4.54°/13.70° 系统性相位差，
全段误差）。文件注释里 Vorbis 分支早就写明「步长 1 逐样本精搜，避免虚假对齐」，
这轮把 MP3 也统一成逐样本，**阈值与比较样本数一律不变**。

### 明确撤回的旧结论

- ❌「≈0.46 样本亚样本相位」—— 真实是整数样本级的对齐伪峰。
- ❌「末帧 bit reservoir 局部畸变」—— 17 帧全部解码成功，reservoir 无问题；
  畸变是**裁剪窗口后移**把过渡区纳入，不是解码器算错。
- ❌「解码器固有延迟需额外前移约 1329 样本、DiagShift 0..640 无解」——
  完整窗口扫描证明零对齐下任何 D 都不达标，问题不在平移量而在重复扣减。
- ❌「固定 6000 窗口 md=0.02348 可作验收」—— 仍不成立，本轮用的是既有
  `CompareWithReferenceAligned` 全重叠口径，没有缩短比较窗口。
