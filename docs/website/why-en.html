01 / Why Yama

No engine on the market
fully belongs to you.

Yama is not trying to be another Unity, nor "a more open Unreal". It addresses a different problem: when you want to understand how an engine actually works, change it, and make it truly yours, almost no desktop engine lets you. This page covers the motivation — why now, why C#, and why three principles come first.

Commercial engines lock the source behind doors. You pay, share revenue, tie your project structure to their asset pipeline — and then get told "that's internal implementation, we can't support that". The problems on the open-source side are just as obvious: many projects have stalled for years, many are teaching demos, and many don't even have a physics rigid body that runs.

Yama takes the third path in between — a desktop engine that is capable, transparent, and truly open. It doesn't promise "easy for everyone". It promises something else: anyone who gets this repository can start reading from any line of code and follow it all the way down to how a Vulkan command buffer gets recorded.

Design Principle

"We are not building a better Unity. We are building a genuinely transparent engine — every layer laid out in the sunlight, readable from any line you start at."

Three non-negotiable principles

These are written down because they drive every technical decision that follows. Compromise any one of them, and Yama slides back to the place we're trying to leave.

  • Code is the documentation. No black boxes. From Vulkan command recording to GJK collision detection, every line lives in the repository — readable, modifiable, removable. The question "how does this module work?" should never exist.
  • Don't reinvent wheels — but don't dodge them either. Math libraries, collision detection, pathfinding, DSP audio — the core systems are all hand-written, not wrappers around someone else's library. You can only control an engine's behavior when you understand every detail.
  • Integrated, not fragmented. Rendering, physics, AI, animation, audio and the editor live in one solution, in one language, cooperating through one RHI abstraction layer. No context-switching across a dozen tools.

Why C#, not C++

The most-asked question, and worth answering first. The answer has two layers: performance, and engineering management.

On performance: the .NET 10 JIT already produces machine code close to C++, and with Span<T>, unsafe and SIMD intrinsics, hot paths can be optimized by hand to be fast enough. Yama's physics engine — GJK / EPA / SAT, all hand-written C# — benchmarks within acceptable range.

On engineering: the real reason is iteration speed. C# development iterates 3–5× faster than C++. Yama is currently driven by one primary maintainer, and speed is everything: validating three ideas in a week beats validating one idea in a month. Once the engine stabilizes, the genuinely bottlenecking hot paths can be bridged with C++ — the YamaEngineBridge project exists precisely for that day.

Why Vulkan is the only backend

The D3D12 backend was written — and then removed from the project. This was not laziness; it was strategy. Maintaining two graphics backends would split one person's time in half, while Vulkan 1.4 covers every modern feature we care about: dynamic rendering, mesh shaders, ray tracing, bindless resources.

The cost: Yama currently runs on Windows only (the WinUI 3 editor depends on it). Linux / macOS via translation layers like MoltenVK is theoretically possible, but it is not the current priority.

What Yama is not

  • Yama is not "a lighter Unity". There is no Store, no Ads, no commercial motive to lock your project format to a private SDK.
  • Yama is not an academic demo. 817 C# source files and 40+ subsystem modules are meant to be run, not exhibited.
  • Yama is not yet an engine you can confidently ship a commercial product with. The honest state is on this page — unfinished work is listed just as clearly as finished work.

Why now

The timing is concrete: Silk.NET turned Vulkan bindings into a single NuGet line in C#; .NET 10's AOT and JIT made managed-code performance no longer a joke; WinUI 3 + ImGui made "Vulkan surface inside a native window" tolerable for the first time. Only when all three hold at once does writing an engine from scratch become realistic.
