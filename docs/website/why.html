01 / Why Yama

市面上的引擎，
没有一个完全属于你。

Yama 不是要再造一个 Unity，也不是要做一个"更开放的 Unreal"。它想解决的是另一个问题 — 当你想理解一个引擎到底怎么工作、想改它、想让它成为自己的东西时，市面上几乎没有任何一个桌面引擎允许你这么做。这一页写清动机：为什么现在做、为什么用 C#、为什么把三条原则摆在最前面。

商业引擎把源码锁在门后。你付钱、分成、把项目结构绑在它的资产管线上，然后被告知"这是内部实现，我们不能支持"。开源引擎另一端的问题同样明显：很多项目停更多年，很多项目只是教学 demo，很多项目连一个能跑的物理刚体都没有。

Yama 想走的是中间的第三条路 — 一个能力完整、代码透明、真正开放的桌面引擎。它不承诺"人人可上手"，它承诺的是另一件事：任何人拿到仓库，都能从任意一行代码开始读，一直读到 Vulkan 命令缓冲是怎么被录制出来的。

Design Principle

"我们不是在做一个更好的 Unity。我们是在做一个真正透明的引擎 — 每一层都摊开在阳光下，你可以从任意一行开始读起。"

三条不可妥协的原则

把这三条写在这里，是因为它们决定了后面所有的技术取舍。任何一条让步，Yama 就会退回到我们想要离开的那个位置。

  • 代码即文档。没有黑盒。从 Vulkan 命令录制到 GJK 碰撞检测，每一行代码都在仓库里，你可以读、可以改、可以拆。不存在"这个模块怎么工作的"这个问题。
  • 不重复造轮子，但也不逃避。数学库、物理碰撞、寻路算法、DSP 音频 — 这些核心系统全部手写实现，不是封装别人的库。理解每一个细节，才能真正控制引擎的行为。
  • 一体化，不碎片化。渲染、物理、AI、动画、音频、编辑器在同一个解决方案里，用同一种语言，通过同一个 RHI 抽象层协作。不需要在十几个工具之间切换上下文。

为什么是 C#，而不是 C++

这是被问得最多的问题，也是最值得先答的一个。答案有两层：性能层的和技术管理层。

性能上，.NET 10 的 JIT 已经能生成接近 C++ 的机器码，配合 Span<T>、unsafe 与 SIMD intrinsics，热路径可以手动优化到足够快。Yama 的物理引擎 — GJK / EPA / SAT 全部手写 C#，基准测试在可接受范围内。

技术上，真正的原因是迭代速度。C# 的开发迭代速度是 C++ 的 3–5 倍。Yama 目前由一个主要维护者推动，速度就是一切：一周能验证三个想法，好过一个月验证一个想法。等引擎稳定之后，真正瓶颈的热路径可以再用 C++ 桥接补上 — YamaEngineBridge 这个工程就是为这一天准备的。

为什么只有 Vulkan 一个后端

D3D12 后端已经写完，也已经从工程中排除。这个决定不是懒惰，是策略：维护两个图形后端会把一个人的时间切成两半，而 Vulkan 1.4 覆盖了我们关心的全部现代特性 — 动态渲染、Mesh Shader、Ray Tracing、Bindless 资源。

代价是 Yama 目前只跑在 Windows 上（因为 WinUI 3 编辑器依赖 Windows）。Linux / macOS 通过 MoltenVK 一类移植层理论上可行，但那不是当前的优先级。

我们不是什么

  • Yama 不是一个"更轻的 Unity"。它没有 Store、没有 Ads、没有把项目格式绑定在私有 SDK 上的商业动机。
  • Yama 也不是一个学术 demo。817 个 C# 源文件、40+ 子系统模块，这些代码是要拿去跑的，不是拿去展示的。
  • Yama 目前也不是一个"可以放心做商业产品"的引擎。真实状态写在 这一页 — 我们把未完成的部分和完成的部分同样清楚地列出来。

为什么现在做

时机其实很具体：Silk.NET 让 Vulkan 绑定在 C# 里变成了一行 NuGet；.NET 10 的 AOT 与 JIT 让托管代码的性能不再是笑话；WinUI 3 + ImGui 让"原生窗口里嵌 Vulkan Surface"第一次变得不恶心。这三件事同时成立，才有了从零写一个引擎的现实可能。
