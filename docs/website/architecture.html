04 / Architecture

六层架构，
一个图形后端。

D3D12 已废弃并从工程中排除。整个引擎只有一个图形后端 — Vulkan 1.4，通过 RHI 抽象层与上层子系统隔离。这意味着只需维护一套图形代码路径。这里把六层结构、模块依赖与这个决策的理由讲透。

为什么"一个后端"是决策，不是偷懒

很多引擎为了兼容性维护两个甚至三个图形后端。Yama 决定只维护一个，理由有三：

  1. 代码路径减半。一套 RHI 抽象、一套命令录制、一套同步逻辑。每修一个 GPU 崩溃，只需修一次。
  2. 特性不妥协。Vulkan 1.4 覆盖 Mesh Shader、Ray Tracing、Bindless、Dynamic Rendering。与其在两个 API 上做"最大公约数"，不如在一个 API 上做全集。
  3. 单人可维护。Yama 目前由一位主要维护者推动，第二个后端是真实的维护税，不是加分项。
Cost

代价是平台受限：Yama 现在只跑在 Windows，因为 WinUI 3 编辑器依赖 Windows。Linux / macOS 通过 MoltenVK 移植层理论上可行，但不是当前优先级。

RHI 抽象：上层永远不碰 Vulkan

RHI 层（21 文件）是引擎与 API 之间唯一的分界。上层子系统只知道 RHICommandBuffer、RHIPipeline、RHIDescriptorSet 这类抽象句柄；真正的 Vulkan 对象被封装在实现里。这是"一个后端"决策得以成立的结构基础 — 如果未来想加后端，RHI 是唯一需要动的地方。

  • 描述符管理：统一管理 UBO / SSBO / Sampler 的绑定，避免上层手写描述符布局。
  • 命令缓冲录制：把渲染命令封装成可重放的命令列表，支持多线程录制。
  • GPU 同步：Fence / Semaphore / 资源屏障封装，上层不直接处理 Vulkan 同步原语。

依赖方向

依赖只允许从上层指向下层，反向依赖通过接口注入。这样，Core & Platform 不依赖任何图形 API，可以被单测覆盖；Vulkan 层只被 RHI 引用，可以被替换。

上层 → 下层

Allowed

Editor → Gameplay → Engine Systems → RHI → Vulkan → Core。

下层 → 上层

Forbidden

Core 不知道 Rendering 存在；Vulkan 不知道 Editor 存在。通过接口注入解耦。
