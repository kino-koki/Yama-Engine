04 / Architecture

Six layers,
one graphics backend.

D3D12 was deprecated and removed from the project. The entire engine has exactly one graphics backend — Vulkan 1.4, isolated from upper subsystems through the RHI abstraction layer. That means only one graphics code path to maintain. This page explains the six layers, the module dependencies, and the reasoning behind that decision.

Why "one backend" is a decision, not laziness

Many engines maintain two or even three graphics backends for compatibility. Yama deliberately maintains one, for three reasons:

  1. Half the code paths. One RHI abstraction, one command recording path, one synchronization logic. Every GPU crash fix only needs to happen once.
  2. No feature compromise. Vulkan 1.4 covers mesh shaders, ray tracing, bindless resources and dynamic rendering. Rather than the "greatest common divisor" of two APIs, take the full set of one.
  3. maintainable by one person. Yama is currently driven by a single primary maintainer; a second backend is a real maintenance tax, not a bonus.
Cost

The cost is platform reach: Yama currently runs on Windows only, because the WinUI 3 editor depends on it. Linux / macOS via a translation layer like MoltenVK is theoretically possible, but is not the current priority.

The RHI abstraction: upper layers never touch Vulkan

The RHI layer (21 files) is the only boundary between the engine and the API. Upper subsystems only know abstract handles like RHICommandBuffer, RHIPipeline and RHIDescriptorSet; real Vulkan objects are encapsulated inside the implementation. This is the structural foundation that makes the "one backend" decision viable — if a new backend is ever added, the RHI is the only place that changes.

  • Descriptor management: unified binding of UBO / SSBO / samplers, so upper layers never hand-write descriptor layouts.
  • Command buffer recording: render commands are wrapped into replayable command lists, supporting multi-threaded recording.
  • GPU synchronization: fences, semaphores and resource barriers are encapsulated; upper layers never handle Vulkan sync primitives directly.

Dependency direction

Dependencies may only point from upper layers to lower ones; reverse dependencies go through interface injection. This way, Core & Platform knows nothing about any graphics API and can be covered by unit tests; the Vulkan layer is only referenced by the RHI and can be replaced.
